# v1.146.0: Remove CLI-spawned harnesses

## Overview

The six CLI-spawned harnesses — `opencode`, `pi`, `cursor`, `claude`, `copilot`, and `commandcode` — are removed, along with their compatibility code. `AgentHarness` is now exactly the five SDK harnesses: `opencode-sdk`, `pi-sdk`, `cursor-sdk`, `claude-sdk`, and `codex-sdk`. Custom agents (`get-next-task`, `register-agent --type=custom`) are unchanged.

Target release: v1.146.0, the next minor after CLI `1.145.1`. The release owner may renumber at release time; only the version in this filename changes.

## Rollout (two PRs, in this order)

Production deploys on merge to master, and the schema push validates existing rows against the narrowed validators. The data purge must therefore run before PR-B lands.

1. Merge PR-A [#1793](https://github.com/conradkoh/chatroom/pull/1793), "feat(backend): add migrations that purge CLI harness data". It adds the purge migrations and changes no schema or behavior.
2. Run `pnpm migrate` with `CONVEX_DEPLOY_KEY` set to production. Confirm it ends with `✅ All migrations completed successfully.` and that `unsetMachineLegacyCapabilityFields` and all seven `purgeRetiredCliHarness*` migrations are complete.
3. Publish the CLI release that carries PR-B's CLI changes, so daemons stop reporting retired harnesses. `.github/workflows/publish-cli.yml` publishes only on a master version bump, so the release owner chooses the mechanism: merge the CLI side first and let the workflow publish, or cut the release from the PR-B branch with `publish:prepare` and publish the resulting tarball (the same steps the workflow runs). This doc does not prescribe one; the requirement is that the published CLI exists before step 4.
4. Immediately before merging PR-B, re-run `pnpm migrate` to catch stragglers written by old daemons between steps 2 and 4. Then merge PR-B [#1794](https://github.com/conradkoh/chatroom/pull/1794). The narrowed schema and validators deploy with it. See [Old-daemon caveat](#old-daemon-caveat) if the schema push fails.

## Data consequences

| Table                                  | Effect                                                                                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `chatroom_machines`                    | `unsetMachineLegacyCapabilityFields` unsets legacy `availableModels`, `availableHarnesses`, `harnessVersions`, `lastSeenAt`. |
| `chatroom_machineModelFilters`         | Deletes rows whose `agentHarness` is a retired CLI harness.                                                                  |
| `chatroom_agentLastSentLaunchRequests` | Deletes rows whose `agentHarness` is a retired CLI harness.                                                                  |
| `chatroom_machineConfigFavorites`      | Removes retired entries from `favorites`. The list may become `[]`.                                                          |
| `chatroom_machineCapabilities`         | Removes retired names from `availableHarnesses` and `harnessVersions`.                                                       |
| `chatroom_machineCommandInbox`         | Deletes queued `agent.requestStart` and `agent.restart` commands for a retired harness. `stop` and other commands are kept.  |
| `chatroom_agentDesiredConfigs`         | Deletes rows for retired harnesses. Deprecated table; this change does not drop it.                                          |
| `chatroom_agentRuntimeStates`          | Deletes rows for retired harnesses. Deprecated table; this change does not drop it.                                          |

Users reconfigure any role that used a retired CLI harness with an SDK harness.

`availableModels` keys and `workspaces[].harnesses[].name` may still hold retired names. They are `v.string()` or record keys, so they do not block the schema narrowing, and the next daemon refresh overwrites them.

## Old-daemon caveat

After PR-B merges, the narrowed `machines.register` and `machines.refreshCapabilities` validators reject any call whose harness list includes a retired name. A daemon that still has a CLI harness installed (for example the `opencode` binary) cannot register or refresh capabilities until it runs the new CLI. Machines with only CLI harnesses lose agent capability by design. No compatibility filter is added.

Between the re-run in step 4 and the PR-B deploy, an old daemon's heartbeat can still re-add a retired harness name to a machine's capability rows. The schema push validates existing rows against the narrowed validators, so a row that still holds a retired name makes the push fail. The push is fail-closed: the deploy is rejected, not applied with those rows. Recovery: re-run `pnpm migrate` with `CONVEX_DEPLOY_KEY` set to production, then redeploy PR-B.

## Verification

- Immediately before merging #1794, and again after the PR-B deploy, each of the seven purged tables must pass the check below: `matches` is `0` and `complete` is `true`, or the dashboard fallback passes for that table.
- After step 2 in each environment, no row in the seven purged tables references a retired harness.
- After PR-B, `AGENT_HARNESSES` in `services/backend/src/domain/entities/agent.ts` equals the five SDK values.

`npx convex run --inline-query` evaluates a read-only query against the deployment `npx convex` selects; add `--prod` to inspect production. Each command below reads a bounded number of rows and returns an object:

- `matches`: rows that still reference a retired harness. Any non-zero value is conclusive: those rows exist, and the step does not pass until they are removed (re-run `pnpm migrate` as in rollout step 4).
- `scanned`: rows read.
- `complete`: `true` when the table was read in full, that is, `scanned` is below the cap.

The cap is 200 rows per table, or 50 for `chatroom_machineCapabilities`, whose rows can be large. A table passes when `matches` is `0` and `complete` is `true`. If `matches` is `0` and `complete` is `false`, the result is inconclusive because rows past the cap were not read. The same applies if a command fails with a read-limit or timeout error. In either case, use the dashboard fallback below for that table.

```bash
# chatroom_machineModelFilters — field: agentHarness
npx convex run --inline-query 'const retired = ["opencode","pi","cursor","claude","copilot","commandcode"]; const rows = await ctx.db.query("chatroom_machineModelFilters").take(200); return { matches: rows.filter((r) => retired.includes(r.agentHarness)).length, scanned: rows.length, complete: rows.length < 200 }'
```

**Dashboard fallback.** If a command is too large to run, or its result is inconclusive, filter that table in the Convex dashboard by retired name instead. Check the field named for that table above, one retired name at a time (`opencode`, `pi`, `cursor`, `claude`, `copilot`, `commandcode`).
