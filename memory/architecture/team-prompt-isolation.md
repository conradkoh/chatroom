# Per-team prompt isolation

## Context

Role prompts for the duo, solo, and trio presets were built from one global role-template catalogue and three separate team if-chains: role guidance in `services/backend/prompts/selector-context.ts`, team context in `services/backend/prompts/sections/team-context.ts`, and role identity in the global catalogue. A wording change for one team's role could change what another team received, and no check showed which teams a change reached. This decision makes each preset team's role prompts depend on that team's own folder, so an edit for one team cannot silently regress another. The handoff graph and session rules are a separate decision: see [Trio team coordination](/architecture/trio-team-coordination.md).

## Invariant

Every role prompt a preset team renders comes from that team's own module under `services/backend/prompts/teams/<team>/` and the registry, so no file under one team folder imports another team folder, and nothing outside `prompts/teams/` reaches team code except through `prompts/teams/registry.ts` or a pinned exception.

## Decisions

1. **Colocation per team.** Each preset team owns `prompts/teams/<team>/prompts/role-identity.ts`, typed `{ readonly [R in BuiltinTeamRole<'<team>'>]: RoleIdentity }`, plus `prompts/team-context.ts` and `prompts/fromContext.ts`. Changing a team's membership is a compile error in that team's identity file only. Duo and solo guidance already lived under team-named paths; trio follows the same layout.
   - Rejected: a shared default identity that teams inherit. Editing the default would change every inheriting team, which is the regression this decision removes. Repeating a title and description across teams is the accepted cost.
2. **One registry dispatches.** `TEAM_PROMPT_MODULES` in `services/backend/prompts/teams/registry.ts` is the only dispatch table for role identity, team guidance, and team context. Each entry satisfies `TeamPromptModule<T>`, so a new preset team must supply all three. Three call sites read it: `selector-context.ts` (`getRoleGuidanceFromContext`), `sections/team-context.ts` (`getTeamContextSection`), and `sections/role-identity.ts` (through `resolveRoleIdentity`).
3. **Fallback chain.** `resolveRoleIdentity({ team, role })` lower-cases `role` and returns the first match:
   1. `team` is a preset and that team's catalogue owns the role: that entry, by reference.
   2. Otherwise: `CUSTOM_TEAM_ROLE_IDENTITY` in `prompts/teams/custom/prompts/role-identity.ts`, a frozen verbatim copy of the former global catalogue. It serves unknown teams and roles outside a preset's membership, such as a legacy persisted role.
   3. Otherwise: `prompts/role-identity-fallback.ts`, which covers the custom `tester` role, ephemeral and retired roles, and a generic identity for anything else.
      Team guidance that returns `null` or throws falls back to base guidance. Team context that is `''` renders nothing.

## Shared-mechanics exceptions

The invariant has one declared exception: mechanics shared across teams stay outside team folders. Their text reaches every team's prompts, so an edit to one shows in every team's characterisation snapshots. Each row lists its reason.

Removing it changes behaviour for those rooms and needs its own snapshot-backed decision. |

The import-boundary guard pins exactly ten outside-to-team imports in `ALLOWED_TEAM_IMPORTS`: the three CLI handoff-template index imports (duo, solo, trio), the solo base-guidance mapping, the two game-asset imports, the three verifier-family imports (verifier, verifier gate guidance, and proof-of-verification), and the package barrel. The guard is in `prompts/teams/team-isolation.test.ts`.

**Known gap.** The guard checks imports from files outside `prompts/teams/` and imports between team folders. It does not check imports made by root-level files directly under `prompts/teams/`. `registry.ts` imports every team by design, and `teams/index.ts` re-exports the duo and solo barrels.

## Consequences

- A prompt edit for one team touches that team's folder and its snapshot. An edit to a shared mechanic changes every team's snapshots, which is intended.
- A new builtin role needs an identity entry in each supported team's catalogue, and also an entry in the frozen custom catalogue, because that type covers every builtin role.
- Duplicate titles and descriptions across teams are accepted.
- Team structures are not versioned. Prompts change in place, and the snapshot diff is the review surface.
